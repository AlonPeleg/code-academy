כל מתחיל ב-React לומד "שמים `key` על פריטי רשימה אחרת React מתלוננת". רוב האנשים עוצרים שם. אבל `key` הוא באמת עניין של **זהות**: איך React יודעת שהדבר שהיא מציירת עכשיו הוא אותו דבר שציירה לפני רגע. ברגע שמבינים את זה, קבוצה שלמה של באגים מוזרים (טקסט בתיבה הלא נכונה, state שנשאר, קלטים שמאבדים פוקוס) מפסיקה להיות מסתורית, ומקבלים כלי שימושי: איפוס state בכוונה.

## איך React מתאימה דברים

אחרי כל שינוי state React מרנדרת שוב את עץ הקומפוננטות שלכם ואז משווה את התוצאה החדשה לקודמת. לכל מקום היא שואלת: האם זה **אותו סוג** של קומפוננטה, ב**אותו מיקום**, עם **אותו key**? אם כן, React שומרת את הקומפוננטה הקיימת ואת ה-**state** שלה ומעדכנת רק את ה-props. אם לא, היא זורקת את הישנה (כולל ה-state) ויוצרת חדשה.

לזה יש תוצאה מפתיעה עבור `Part1` בתרגיל. `useState("Hello " + user)` משתמשת בארגומנט שלה רק בפעם הראשונה. כש-`user` משתנה מ-Ada ל-Grace, ה-`Draft` הוא אותו סוג באותו מקום, ולכן React **שומרת** אותו, יחד עם הטקסט הישן שלו. הדף ממשיך להציג "Hello Ada" ליד Grace.

## מפתחות כתוויות זהות

key הוא תווית שם שמניחים על אלמנט:

```jsx
<Draft key={user} user={user} />
```

כשה-key משתנה מ-`"Ada"` ל-`"Grace"`, React מחליטה "זו קומפוננטה אחרת", מסירה (unmount) את הישנה ומרכיבה (mount) חדשה. ה-state שלה מתחיל שוב מהערך ההתחלתי, וזה מה שרצינו. זו הדרך הסטנדרטית לאפס קומפוננטה כשמשהו שהיא תלויה בו משתנה, כמו `key={userId}` על טופס עריכה. (`key` מיוחד: React עצמה משתמשת בו והוא **לא** מועבר הלאה, ולכן הקומפוננטה לא יכולה לקרוא את `props.key`.)

## מפתחות ברשימות

ברשימה ה-key אומר איזה פריט הוא איזה, גם כשפריטים מתווספים, מוסרים או משנים סדר:

```jsx
{people.map((p) => <Row key={p.id} name={p.name} />)}
```

ה-key חייב להיות **ייחודי בין אחים** ו**יציב**: אותו פריט מקבל תמיד אותו key. id ממסד נתונים, שם משתמש או מונה שהקצתם בזמן יצירת הפריט הם מפתחות טובים.

למה לא האינדקס? עם `key={index}` המפתח מתאר את ה**מיקום**, לא את הפריט. מסירים את האדם הראשון והשורה השנייה הישנה מקבלת עכשיו אינדקס 0. React רואה "מפתח 0 עדיין כאן" ושומרת את הקומפוננטה וה-state של השורה הזו, ופשוט נותנת לה props חדשים. בתרגיל כל `Row` זוכרת מספר יצירה. עם מפתחות אינדקס, Grace יורשת את המספר `#1` של Ada. עם id אמיתיים, Grace שומרת על `#2` שלה, בדיוק כמו שהייתם מקווים. באפליקציה אמיתית ה-state שנשאר יכול להיות הערה שהוקלדה חצי, תיבת סימון מסומנת או מיקום גלילה שמסתיימים מחוברים לאדם הלא נכון.

מפתחות אינדקס בסדר רק כשהרשימה **סטטית**: היא אף פעם לא משנה סדר, לא מסוננת ולא נערכת באמצע, ולפריטים אין state משלהם.

> **שימו לב:**
> - `Warning: Each child in a list should have a unique "key" prop`: שכחתם את ה-key, או ששמתם אותו על אלמנט פנימי במקום על האלמנט שמוחזר מ-`map`.
> - `Warning: Encountered two children with the same key`: המפתחות שלכם לא ייחודיים, למשל אותו שם פעמיים.
> - `key={Math.random()}` או `key={Date.now()}` בזמן רינדור: ה-key משתנה בכל רינדור, ולכן כל פריט נהרס ונבנה מחדש בכל פעם. קלטים מאבדים פוקוס אחרי כל הקשה.
> - ניסיון לקרוא `props.key` בתוך הקומפוננטה: הוא תמיד `undefined`. העבירו את הערך שוב בשם אחר אם אתם צריכים אותו.

## ממשיכים הלאה

הוסיפו ל-`Part2` כפתור Reverse שקורא ל-`setPeople([...people].reverse())`. עם `key={p.id}` כל שורה שומרת על המספר שלה בזמן שהיא זזה; עם `key={index}` המספרים נשארים במקום והשמות זזים.

> **תורכם:** ב-`Part1` הוסיפו key ל-`Draft` כך שיתחיל מחדש לכל משתמש. ב-`Part2` השתמשו ב-id של כל אדם כ-key. הדף אמור אז להציג את הטיוטה של Grace, ואת השורות `Grace #2` ו-`Linus #3`.
