רוב האנשים כותבים קודם את הקוד ואחר כך את הבדיקות (אם בכלל). **פיתוח מונחה בדיקות** (Test-driven development, או TDD) הופך את הסדר: כותבים קודם את הבדיקה, רואים אותה נכשלת, ורק אז כותבים את הקוד שגורם לה לעבור. זה נשמע מוזר, אבל זה נותן צעדים קטנים, משוב מיידי ורשת ביטחון, ומכריח לחשוב *מה* הקוד צריך לעשות לפני *איך*.

## המחזור: אדום, ירוק, refactor

1. **אדום (Red).** כתבו בדיקה קטנה אחת להתנהגות שעדיין לא קיימת. הריצו את הבדיקות: היא חייבת **להיכשל**. (אם היא עוברת, הבדיקה חסרת תועלת, או שהתכונה כבר קיימת.)
2. **ירוק (Green).** כתבו את הקוד ה**פשוט ביותר** שגורם לבדיקה לעבור. לא הטוב ביותר, לא הכללי ביותר: הפשוט ביותר. זה בסדר להיות קצת טיפשי, למשל להחזיר ערך קבוע.
3. **Refactor.** כשכל הבדיקות ירוקות, נקו: הסירו כפילויות, שפרו שמות, פשטו. הריצו את הבדיקות אחרי כל שינוי. אם הן נשארות ירוקות, לא שברתם כלום.

אחר כך מתחילים שוב עם הבדיקה הבאה. כל סבב לוקח דקה או שתיים.

## דוגמה קטנה

אנחנו רוצים את `isAdult(age)`. סבב 1, **אדום**:

```js
it("is false for a child", () => {
  expect(isAdult(10)).toBe(false);
});
```

היא נכשלת כי `isAdult` לא קיימת. **ירוק**, הקוד הפשוט ביותר:

```js
function isAdult(age) {
  return false;
}
```

טיפשי, אבל ירוק! סבב 2, שוב **אדום**:

```js
it("is true for an adult", () => {
  expect(isAdult(30)).toBe(true);
});
```

עכשיו התשובה הקבועה לא מספיקה, ולכן אנחנו נאלצים לכתוב את ההיגיון האמיתי (**ירוק**):

```js
function isAdult(age) {
  return age >= 18;
}
```

בדיקה שלישית לגבול (`isAdult(18)` היא `true`, `isAdult(17)` היא `false`) באה אחר כך. הבדיקות מתארות את ההתנהגות מקרה אחר מקרה, והקוד גדל רק עד כמה שהבדיקות דורשות.

## למה זה עוזר

* **צעדים קטנים.** כשמשהו נשבר, אתם יודעים שזה היה השינוי הקטן האחרון.
* **תכנון טוב יותר.** קוד שקל לבדוק (פונקציות קטנות, קלטים ופלטים ברורים) בדרך כלל גם קל יותר להבין.
* **רשת ביטחון.** סוויטת הבדיקות המוגמרת מאפשרת לכם לעשות refactor ולהוסיף תכונות בלי פחד.
* **תיקון באגים.** כשמוצאים באג, קודם כותבים בדיקה שמשחזרת אותו (אדום), ואז מתקנים (ירוק). הבאג לא יכול לחזור בשקט.

TDD הוא כלי, לא דת. מפתחים רבים משתמשים בו לקוד עתיר היגיון (מפענחים, חישובים, ולידציה) וכותבים בדיקות בדיעבד לקוד חיבור. כדאי ללמוד את ההרגל אדום-ירוק בכל מקרה.

## התרגיל: slugify

**Slug** הוא הצורה הידידותית ל-URL של כותרת: `"Hello, World!"` הופכת ל-`"hello-world"`. קיבלתם שש בדיקות, שמתארות את ההתנהגות, ופונקציה שעדיין לא עושה כלום. עברו עליהן לפי הסדר כמו בסשן TDD: גרמו לבדיקה הראשונה שנכשלת לעבור עם השינוי הפשוט ביותר, הריצו, ואז הבאה, וכך הלאה. כלים שימושיים הם `toLowerCase()` ו-`replace()` עם ביטוי רגולרי: `/[^a-z0-9]+/g` מתאים לכל רצף של תווים שאינם אותיות או ספרות.

כשכל שש הבדיקות ירוקות, הוסיפו תכונה חדשה בדרך של TDD. קודם כותבים את הבדיקה (אדום), ואז את הקוד (ירוק).

> **שימו לב:**
> * **כותבים קודם בדיקה גדולה.** בדיקה שדורשת חמש תכונות בבת אחת לא יכולה להפוך לירוקה מהר. שמרו כל בדיקה על התנהגות אחת.
> * **מדלגים על שלב האדום.** לפעמים תכתבו בדיקה שעוברת מיד. שאלו למה: האם ההתנהגות כבר קיימת, או שהבדיקה שגויה?
> * **הופכים לירוק על ידי עריכת הבדיקה.** שינוי הערך המצופה כך שיתאים לפלט שגוי מבטל את המטרה.
> * **שוכחים לעשות refactor.** קוד ירוק שמלא בהעתק-הדבק הוא חוב. השתמשו ברשת הביטחון וסדרו.
> * **הדגל `g` בביטוי רגולרי.** `replace(/x/, "-")` בלי `g` מחליפה רק את ההתאמה הראשונה. השתמשו ב-`/x/g` כדי להחליף את כולן.

> **תורכם:** גרמו לשש הבדיקות הנתונות לעבור ב-`slugify.js`. אחר כך החליפו את `it.todo` ב-`slugify.test.js` בבדיקה אמיתית בשם `cuts the slug to maxLength without a trailing dash` שמצפה ש-`slugify("hello big world", 10)` תהיה `"hello-big"` (ראו אותה נכשלת קודם), והוסיפו ל-`slugify` את הפרמטר האופציונלי `maxLength`. הדוח חייב להסתיים ב-`Tests: 7 passed, 7 total`.
