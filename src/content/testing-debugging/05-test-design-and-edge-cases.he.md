בדיקה שבודקת רק את "המסלול השמח" (הקלט הרגיל והנעים) היא כמו בדיקת מכונית רק על כביש ישר וריק. רוב הבאגים מסתתרים ב**קצוות**: רשימות ריקות, אפס, מספרים שליליים, ערכים חוזרים. בשיעור הזה תלמדו לתכנן בדיקות טובות, לא רק לכתוב אותן, ותראו בדיקות שתופסות שני באגים אמיתיים.

## רעיון אחד בכל בדיקה

תנו לכל בדיקה **סיבה אחת להיכשל**, ושם שאומר מהי ההתנהגות. השוו:

```js
it("works", () => { ... 12 expect lines ... });                 // which part broke?
it("averages the two middle values for an even count", ...);    // clear!
```

כשבדיקה נכשלת, השם שלה צריך לספר לכם מה שבור עוד לפני שאתם קוראים את הקוד. שם טוב הוא משפט: "עושה X כש-Y".

## Arrange, Act, Assert

ברוב הבדיקות יש שלושה חלקים, בסדר הזה:

```js
it("adds an item to the cart", () => {
  // Arrange: create what you need
  const cart = [];
  // Act: do the one thing you are testing
  cart.push("apple");
  // Assert: check the outcome
  expect(cart).toEqual(["apple"]);
});
```

הפרדה בין החלקים (גם רק בשורות ריקות) הופכת את הבדיקות לקלות לקריאה. אם בחלק ה-*Act* יש שלוש קריאות שונות, כנראה שאתם בודקים שלושה דברים.

## חשבו על מקרי קצה

עבור כל פונקציה, עברו על הרשימה הזאת וכתבו בדיקה לכל סעיף שיש בו היגיון:

* **ריק:** `""`, `[]`, `{}`, `0`.
* **פריט אחד**, ו**שני פריטים** (לולאות נשברות לעיתים קרובות בסבב הראשון או האחרון).
* **גבולות:** אם הגבול הוא 10, בדקו 9, 10 ו-11.
* **מספרים שליליים או ענקיים**, ומספרים עשרוניים.
* **קלט שגוי:** `null`, `undefined`, סוג שגוי. החליטו מה צריך לקרות (שגיאה, ערך ברירת מחדל) ובדקו את זה.
* **תופעות לוואי:** האם הפונקציה משנה את הנתונים שנתתם לה? פונקציה שממיינת את "הקלט שלה" במקום יכולה להפתיע את מי שקרא לה.

פונקציית ה-median בשיעור הזה נראית תקינה עבור `[3, 1, 2]`, אבל מקרי הקצה חושפים שני באגים. אתם מצליחים לזהות אותם לפני שמריצים את הבדיקות? `[10, 9, 1].sort()` מחזיר `[1, 10, 9]`, כי בלי פונקציית השוואה `sort` הופכת פריטים ל**טקסט** (ו-`"10"` בא לפני `"9"`). ובנוסף, `sort` משנה את המערך שהועבר אליה, וזה לא נעים למי שקרא לפונקציה.

## בדיקת שגיאות

אם ההתנהגות הנכונה היא לזרוק שגיאה, בדקו את זה. צריך לתת ל-`expect` **פונקציה**, כדי שה-matcher יוכל לקרוא לה בצורה בטוחה:

```js
expect(() => median([])).toThrow();                  // any error
expect(() => median([])).toThrow("at least one");    // message contains this text
```

## הרבה מקרים, גוף בדיקה אחד

כשיש רשימה של קלטים ותוצאות, `it.each` מונעת חזרה על אותו קוד:

```js
it.each([
  [[1], 1],
  [[1, 3], 2],
  [[5, 1, 3], 3],
])("median of %s", (numbers, expected) => {
  expect(median(numbers)).toBe(expected);
});
```

כל שורה הופכת לבדיקה נפרדת. השתמשו בזה כשהמקרים הם "אותה צורה, נתונים שונים".

> **שימו לב:**
> * **קוראים לפונקציה בתוך `expect` כשבודקים שגיאה.** `expect(median([])).toThrow()` נכשלת עם השגיאה המקורית, כי `median([])` כבר רצה וזרקה שגיאה לפני ש-`expect` הספיקה לעשות משהו.
> * **מספרים עשרוניים (floating-point).** `0.1 + 0.2` הוא `0.30000000000000004`. השתמשו ב-`toBeCloseTo(0.3)` במקום ב-`toBe(0.3)`.
> * **בדיקות שתלויות זו בזו.** כל בדיקה חייבת ליצור לעצמה את הנתונים. אם בדיקה עוברת רק אחרי שבדיקה אחרת רצה, שינוי בסדר ישבור הכול.
> * **מעתיקים את המימוש לתוך הבדיקה.** אם הבדיקה מחשבת את הערך המצופה באותו היגיון כמו הקוד, היא לא יכולה לתפוס טעות באותו היגיון. כתבו את הערך המצופה ידנית.

> **תורכם:** החליפו את ארבע שורות `it.todo(...)` ב-`stats.test.js` בבדיקות אמיתיות (באותם שמות). חלק מהן ייכשלו: הן מצאו באגים ב-`stats.js`. תקנו את `median` (מיינו עותק עם פונקציית השוואה) עד שהדוח יראה `Tests: 5 passed, 5 total`.
