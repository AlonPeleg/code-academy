JavaScript עושה דבר אחד בכל פעם, ובכל זאת היא יכולה לחכות לטיימרים, לתשובות מהרשת ולקליקים בלי להיתקע. הסוד הוא **לולאת האירועים** (event loop). אם תבינו אותה, באגים מוזרים כמו "למה ה-log הופיע לפני הנתונים?" ו"למה הדף תקוע?" מפסיקים להיות תעלומה.

## החלקים

- **מחסנית הקריאות (call stack).** ערימת הפונקציות שרצות עכשיו. JavaScript יכולה להריץ רק את הפונקציה שבראש הערימה.
- **Web APIs / סביבת ההרצה (host).** טיימרים, הרשת וקליקים מטופלים מחוץ לקוד שלכם, על ידי הדפדפן (או Node). כשהם מוכנים הם מוסרים קולבק.
- **תור ה-tasks** (נקרא גם תור ה-macrotasks). קולבקים של `setTimeout`, של `setInterval`, של קליקים ושל אירועים דומים מחכים כאן, task אחד בכל תור.
- **תור ה-microtasks.** קולבקים של promises (`.then`, `.catch`, `.finally`), של `queueMicrotask(fn)` והקוד שאחרי `await` מחכים כאן. יש לו **עדיפות** על פני תור ה-tasks.

## הלולאה, בצעדים פשוטים

1. מריצים את הסקריפט הנוכחי עד שמחסנית הקריאות ריקה (גם זה בעצמו task אחד).
2. מריצים את **כל** ה-microtasks, עד שתור ה-microtasks ריק לגמרי. גם microtasks שמכניסים לתור microtasks נוספים רצים עכשיו.
3. (הדפדפן עשוי לצייר מחדש את המסך כאן.)
4. לוקחים **task אחד** מתור ה-tasks ומריצים אותו. חוזרים לצעד 2.

זה הכול. כל השאר הוא תוצאה של זה.

```js
console.log("1 sync");
setTimeout(() => console.log("4 timer"), 0);
Promise.resolve().then(() => console.log("3 microtask"));
console.log("2 sync");
// prints: 1 sync, 2 sync, 3 microtask, 4 timer
```

`setTimeout(fn, 0)` לא אומר "עכשיו". הוא אומר "כ-task חדש, בהקדם האפשרי", ובכל מקרה זה תמיד אחרי הקוד הנוכחי **וגם** אחרי כל ה-microtasks.

## ומה עם async ו-await?

פונקציית `async` רצה **באופן סינכרוני** עד ה-`await` הראשון שלה. ב-`await`, שאר הפונקציה נקבע לריצה כ-microtask לרגע שבו ה-promise שממתינים לו מסתיים, והקורא ממשיך.

```js
async function f() {
  console.log("a");   // runs immediately when f() is called
  await null;
  console.log("c");   // microtask, later
}
f();
console.log("b");
// prints: a, b, c
```

## למה זה חשוב: חסימה ו-yield

כל עוד הפונקציה שלכם רצה, **שום דבר אחר לא יכול לרוץ**: לא קליקים, לא טיימרים ולא ציור מחדש. לולאה שעובדת חמש שניות מקפיאה דף למשך חמש שניות. הפתרון הוא לחתוך את העבודה לחתיכות ו**לוותר על התור** (yield) ביניהן, כלומר לתת ללולאת האירועים להסתובב פעם אחת. הוויתור חייב לעבור דרך תור ה-**tasks** (דרך `setTimeout`), כי ה-microtasks מתרוקנים לפני כל task, ולכן המתנה ל-promise שכבר הסתיים לא נותנת לאף אחד אחר תור. בתרגיל תראו את זה במו עיניכם: ה"טיימר" שממתין מקבל את התור שלו מיד אחרי החתיכה הראשונה.

> **שימו לב:**
> - להניח ש-`setTimeout(fn, 0)` רץ לפני קולבק של promise. קולבקים של promise מנצחים.
> - לכתוב שרשרת אינסופית של microtasks (`then` שתמיד מכניס `then` נוסף). תור ה-tasks אף פעם לא מקבל תור, ולכן טיימרים לא יורים והדף נתקע.
> - להאמין ש-`await` משהה את התוכנית כולה. הוא משהה רק את פונקציית ה-async הנוכחית; שאר התוכנית ממשיכה לרוץ.
> - לשכוח שהקוד שלפני ה-`await` הראשון של פונקציית async רץ באופן סינכרוני.
> - להסתמך על דיוק מושלם של טיימר. טיימר הוא השהיה מינימלית ולא הבטחה: אם המחסנית עסוקה, הקולבק פשוט מחכה יותר.
> - לשים עבודה כבדה ב-event handler ולתהות למה הכפתור "לא מגיב". פצלו את העבודה או העבירו אותה ל-Web Worker.

## להמשיך הלאה

נבאו את הפלט של החידה אחרי שתוסיפו `await null;` נוסף בתוך פונקציית ה-async, או אחרי ששניתם את ההשהיה של `setTimeout` ל-`10`. אחר כך הריצו והשוו. ב-Node.js יש גם `process.nextTick`, שרץ עוד לפני microtasks של promises.

> **תורכם:** נבאו את סדר החידה ומלאו את `prediction`, ואז כתבו את `tick()` כך שהטיימר יקבל את התור שלו אחרי החתיכה הראשונה. הפלט הצפוי מוצג למעלה בבדיקה.
